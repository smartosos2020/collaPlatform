# 知识库实时协作服务：什么时候需要启动

## 1. 先看结论

> 判断标准不是“平台是否有多人登录”，而是“是否打开并编辑知识库 Markdown 正文”。

- 只使用项目空间、工作项、审批、搜索、消息和系统设置时，不需要启动知识协作服务。
- 准备打开或编辑知识库 Markdown 正文时，建议启动。
- 即使只有一个人编辑知识正文，按照当前实现也应启动。
- 需要多人同时编辑、查看在线成员和实时光标、自动合并修改时，必须启动。

启动命令：

```shell
pnpm collaboration:start
```

默认服务地址为 `http://127.0.0.1:1234`，浏览器通过 `ws://localhost:1234` 建立知识正文协作连接。

## 2. 这个服务负责什么

`pnpm collaboration:start` 启动的是知识库正文专用的 Hocuspocus/Yjs 协作服务，主要负责：

1. 建立知识文档的实时 WebSocket 会话。
2. 校验后端签发的知识协作票据和当前编辑权限。
3. 同步标题和正文修改。
4. 展示在线协作者和实时光标。
5. 合并多人并发修改，减少互相覆盖。
6. 暂存 Yjs 更新，并通过后端把更新和快照持久化。
7. 使用 Redis 协调协作状态；本地配置默认启用 Redis。

它不负责下列功能：

- 项目空间成员、任务模板、字段、流程和权限配置。
- 工作项的新建、查询和流转。
- 审批、搜索、通知和即时消息的普通接口。
- 平台通用的 `/ws/events` 实时事件通道；该通道由后端 `8080` 端口提供。

因此，“多人共同使用项目空间”本身不会要求启动这个服务；只有进入知识正文协作链路时才会用到它。

## 3. 按使用场景判断

| 使用场景 | 是否启动 | 原因 |
| --- | --- | --- |
| 项目空间配置、成员管理、工作项和项目管理 | 不需要 | 这些功能使用后端 REST API 和平台事件通道 |
| 审批、全局搜索、通知、即时消息 | 不需要 | 不经过知识正文 Yjs 服务 |
| 查看知识库列表、目录或管理知识库 | 通常不需要 | 基础数据由后端 REST API 提供 |
| 打开 Markdown 知识正文阅读 | 建议启动 | 当前前端会为所有 Markdown 正文尝试建立协作 Provider |
| 单人编辑 Markdown 知识正文 | 需要 | 当前编辑器会切换到 Yjs 保存链路，不再按普通 REST 自动保存 |
| 多人同时编辑同一篇知识正文 | 必须启动 | 在线状态、光标、实时同步和冲突合并均依赖它 |
| 调试知识协作、离线恢复或协作权限 | 必须启动 | 这些就是该服务提供的能力 |

## 4. 为什么单人编辑也需要启动

从产品职责看，它是“多人实时编辑服务”；但当前代码不是等第二位用户进入后才启用。

实际链路如下：

```text
打开 Markdown 知识正文
        ↓
后端签发协作票据
        ↓
前端立即创建 Yjs/Hocuspocus Provider
        ↓
编辑器切换到协作文档和协作保存链路
        ↓
协作服务把更新持久化到后端
```

当前有四个需要注意的行为：

1. 所有 Markdown 知识正文都会启用实时协作 Hook，与当前在线人数无关。
2. 后端签发票据时不会先探测 `1234` 端口是否健康，因此协作服务未启动时仍可能成功拿到票据。
3. 前端拿到票据后会创建 Provider；只要 Provider 已创建，普通 REST 正文自动保存就会停止。
4. 服务连接失败后，修改只能等待协作通道恢复，不能把它当成稳定的“单人 REST 编辑模式”。

如果票据请求本身失败，Provider 可能保持为空，页面可能暂时走普通 REST 分支。但这属于异常情况下的偶然降级，不应作为本地运行方式依赖。

## 5. 未启动时会发生什么

对非知识正文功能：

- 项目空间、工作项等功能可以继续使用。
- 后端 `8080` 的平台实时事件通道不受这个进程直接影响。

对 Markdown 知识正文：

- WebSocket 会连接失败，页面可能持续显示“正在同步”、断开或离线状态。
- 在线成员、实时光标和多人修改同步不可用。
- 当前页面内产生的 Yjs 修改可能暂存在内存中，等待重新连接。
- 页面提供离线修改计数和导出副本能力，但这不等于已经保存到后端数据库。
- 在恢复连接并确认同步完成前刷新或关闭页面，存在丢失未持久化修改的风险。

因此，如果误在服务未启动时进入了编辑状态，应先启动服务并等待页面显示“实时已同步”；如果无法恢复，应先导出离线副本，再刷新页面。

## 6. 推荐的本地启动组合

### 6.1 只试用项目空间和常规功能

需要：

1. PostgreSQL、Redis、MinIO。
2. 后端服务，默认端口 `8080`。
3. Web 前端，默认端口 `5173`。

知识协作服务可以不启动。

### 6.2 试用知识正文或完整功能

建议按以下顺序启动：

1. 启动 PostgreSQL、Redis、MinIO。
2. 启动后端并确认 `8080` 可访问。
3. 在仓库根目录运行 `pnpm collaboration:start`。
4. 启动 Web 前端。
5. 打开知识正文，等待“实时已同步”后再编辑。

知识协作服务默认依赖：

| 依赖 | 默认地址 | 用途 |
| --- | --- | --- |
| 后端内部接口 | `http://127.0.0.1:8080/api/internal/knowledge-collaboration` | 权限校验、文档加载和持久化 |
| Redis | `127.0.0.1:6379` | 协作节点状态协调 |
| 协作服务端口 | `1234` | WebSocket、健康检查和指标 |

开发服务需要监听代码变化时，可以改用：

```shell
pnpm collaboration:dev
```

## 7. 怎样确认服务已经可用

启动后可在 PowerShell 中检查：

```powershell
Invoke-RestMethod http://127.0.0.1:1234/health
Invoke-RestMethod http://127.0.0.1:1234/ready
```

- `/health` 用于确认协作进程正在响应。
- `/ready` 还会检查协作持久化链路是否已经具备接流量条件，更适合判断能否开始编辑。

页面侧还应确认：

1. 知识正文不再显示离线或连接错误。
2. 顶部出现“实时已同步”。
3. 修改后同步状态能够恢复为已同步。

停止服务时，在运行该命令的终端按 `Ctrl+C`。停止前应先确认知识正文没有等待同步的修改。
